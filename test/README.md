# Live integration harness

`harness.mjs` is a manual integration harness, not a unit-test framework. Run it with Node 18 or newer against an already-running **isolated** Herdr server. Start that server with the same exported environment used by the harness:

```sh
ROOT=$(mktemp -d /tmp/herdr-autorun-check-XXXXXX)
mkdir -p "$ROOT/home" "$ROOT/config" "$ROOT/data"
export HERDR_AUTORUN_TEST_ROOT="$ROOT"
export HERDR_SOCKET_PATH="$ROOT/herdr.sock"
export HERDR_CONFIG_PATH="$ROOT/config.toml"
export HOME="$ROOT/home"
export XDG_CONFIG_HOME="$ROOT/config"
export XDG_DATA_HOME="$ROOT/data"

node test/harness.mjs
```

The harness requires an existing disposable directory strictly below the real `os.tmpdir()` or `/tmp` (including macOS `/tmp` → `/private/tmp` aliases). If Herdr is not on `PATH`, set `HERDR_BIN_PATH` to its executable. It refuses to run without `HERDR_SOCKET_PATH` and `HERDR_AUTORUN_TEST_ROOT`, or if isolated state paths escape the disposable root; missing socket/config files are permitted. A regular file where a path needs a directory is refused.

Use the same Node version in the server's `PATH` and for the harness. Install the checkout's dependencies as described in the root README, and rebuild only `fs-ext` with `npm rebuild fs-ext --ignore-scripts=false` under that Node version before starting the server. Rebuild when switching Node versions: linking the plugin does not guarantee that an existing native addon matches the runtime ABI.

After checking `herdr status`, the harness snapshots any previously selected pane (an empty server is supported), creates its own uniquely labeled workspace, links the checkout as `han.tab-autorun`, and temporarily replaces that isolated plugin's `rules.toml`. It creates disposable fixture directories and tabs only in its owned workspace; no preexisting workspace is used as a test target or closed. Five automatic cases retain command matching, no-match and explicit skip decisions, no `pane.created` autorun after a split, and duplicate hook claims. The first additional case starts with fresh isolated state and a one-slot, long-window automatic rate limit: a successful automatic attempt consumes its pane claim and the rate slot; a competing new tab records `rate_limited` and no effect. A different append-only manual command invoked twice in the **original same** pane must produce exactly two file lines and no output in the competing pane. The default generous-rate fixture is restored afterward.

Ownership is recorded from each creation response's `terminal_id`, checked against the pre-operation inventory: the workspace's initial root, every new tab root, the manual secondary split, and the automatic split fixture. A new pane ID or membership in a created tab/workspace is not ownership. A trustworthy returned terminal identity is retained before visibility confirmation, so a later failed query does not erase it.

Manual cases invoke the real `herdr plugin action invoke han.tab-autorun.run-here` command without pane/tab flags. They temporarily focus only owned workspace/tab/panes, scrub inherited caller IDs, verify returned context workspace/tab/focused-pane IDs, and poll the returned `log.log_id` through `herdr plugin log list` until `succeeded` or `failed`. CLI exit status 0 only proves dispatch, not completion. Unique marker files **and** selected-pane output prove execution, while the other pane must show no effect. Root and secondary panes with different cwd rules, a same-ID layout swap, an observed non-shell foreground held through readiness timeout, and a uniquely sourced `report-agent` guard are covered. The latter checks the reported `pane.agent` field and releases only that fixture's source; it does not claim a real authenticated agent was launched. Missing/conflicting/moved target boundaries are covered by action behavior tests, not CLI flags. Direct hook invocation for the automatic duplicate test inherits the isolated server's full environment, including PATH, HOME, XDG directories, and socket.

Every pane-output assertion, including marker absence in another pane, requires a successful `pane read`; a failed read fails the case rather than proving absence. The busy case requires valid positive integer shell PID and foreground PGID values that differ, both before invocation and after the readiness timeout. Missing or malformed process information is unknown, not evidence of a busy foreground.

Cleanup releases only its uniquely sourced report-agent fixture, resolving the terminal's current pane, and restores the original terminal's current focus before teardown. It closes only registered terminal panes still in the harness workspace, refreshing identity and scope immediately before each `pane close` and confirming terminal disappearance. It never explicitly closes a tab or workspace. Herdr's automatic removal after the final pane closes is confirmed through a successful workspace list; a `pane_not_found` close is accepted only when a successful inventory confirms that terminal is gone. Other close errors remain failures.

Foreign terminals in tracked or untracked tabs, owned terminals moved to another workspace, ambiguous/unavailable inventory, unproven creation provenance, or a workspace that remains present cause incomplete cleanup and exit status 1. These resources and the fixture directory are retained, with identifying details and the directory path printed. Do not remove a retained directory while surviving terminals might use its cwd or files. The original terminal is restored again after pane cleanup; a closed original is never replaced with an unrelated pane. Plugin unlink and prior rules restoration run independently even after cleanup errors. The caller still owns the isolated server and its HOME/XDG directories.

The CLI closes by pane ID, without an expected-terminal compare-and-close operation. Rechecking limits but cannot atomically exclude a move or replacement between the final lookup and close. Avoid concurrent pane mutations during teardown; the harness does not claim race-free protection against arbitrary concurrent changes.

Verified on macOS: Herdr 0.9.0 with Node 18.20.8 passed all nine live cases on a fresh empty server; Herdr 0.9.3 with Node 26.10.0 passed all nine both on an empty server and with existing caller focus. Normal runs exited 0 with no harness-owned panes, workspace, fixture directory, or linked plugin remaining; the existing caller terminal and workspace were preserved. Project checks and all 50 registered tests passed on both Node versions. The agent-protection case uses reported metadata, not an authenticated coding-agent process; Linux remains unverified.

Additional Herdr 0.9.3 runs moved the original caller terminal into a new untracked tab and, separately, into a tracked split tab inside the harness workspace. Both passed all nine functional cases but correctly exited 1 for retained resources: the caller terminal survived at its new pane ID, was finally focused, and its other workspace survived. Moving a harness-owned terminal into a caller workspace likewise passed all nine cases, retained that terminal and its fixture directory, preserved original focus, and exited 1.

A controlled creation-response probe removed `terminal_id` from one real tab-create response. The affected case failed, the remaining eight passed, and the harness exited 1 while preserving the unclassified native terminal and its fixture directory. Plugin unlink still completed, and prior rules bytes and permissions were restored. Unit regressions additionally cover failed visibility confirmation, ambiguous inventory, read errors, missing PGID, and closed-original focus without fallback.

## Manual onboarding acceptance (proposed; not a completed live result)

Use a fresh **isolated** macOS Herdr server and disposable directories with the exported HOME/XDG/socket/config variables above; never use a personal session or repository with unreviewed commands. Install dependencies with the scoped `fs-ext` rebuild under the server's Node version, link this checkout, and check `herdr status`. Record the server/Node versions, each action's returned `log.log_id`, final plugin-log status, and pane output separately. `herdr plugin action invoke <FULL_ACTION_ID>` returns dispatch status, not action completion: poll `herdr plugin log list --plugin han.tab-autorun` for that ID's terminal status. Use the harness's owned-workspace/terminal-ID inventory, focus checks, successful `pane read` checks, original-focus restoration, and conservative cleanup rules above; `node test/harness.mjs` already covers claims, rate limiting, busy foreground, agent metadata, selected-pane scope, and split guards. Do not create a second harness for these cases.

For reproducible disposable cwd fixtures (create these only beneath the isolated root), use:

```sh
mkdir -p "$HERDR_AUTORUN_TEST_ROOT/proof-repo" "$HERDR_AUTORUN_TEST_ROOT/other-repo"
git -C "$HERDR_AUTORUN_TEST_ROOT/proof-repo" init -q
git -C "$HERDR_AUTORUN_TEST_ROOT/proof-repo" -c user.name=Probe -c user.email=probe@example.invalid commit -q --allow-empty -m probe
git -C "$HERDR_AUTORUN_TEST_ROOT/proof-repo" worktree add -q -b linked-probe "$HERDR_AUTORUN_TEST_ROOT/proof-linked"
git -C "$HERDR_AUTORUN_TEST_ROOT/other-repo" init -q
```

These are disposable directory labels, not guaranteed `repo_name` values. Before invoking actions or creating proof tabs, record the pre-creation workspace/pane inventory and create an owned workspace with `herdr workspace create --cwd "$HERDR_AUTORUN_TEST_ROOT/proof-repo"`; capture its returned opaque workspace and root-pane/terminal IDs. A workspace created this way may initially have **no worktree context**. Attach the ordinary checkout with `herdr worktree open --workspace <RETURNED_WORKSPACE_ID> --path "$HERDR_AUTORUN_TEST_ROOT/proof-repo" --focus`, then inspect `herdr plugin action invoke han.tab-autorun.doctor` in that owned context and poll its log. Record its actual `repo_name`, `repo_root`, `cwd`, and `is_linked_worktree`; require an identified repository and `is_linked_worktree = false`. Attach the linked path to that **same** workspace with `herdr worktree open --workspace <RETURNED_WORKSPACE_ID> --path "$HERDR_AUTORUN_TEST_ROOT/proof-linked" --focus`; capture the returned pane/terminal identity and run doctor in this context too. Require `is_linked_worktree = true` and the same observed `repo_name` and intended repository root as the ordinary checkout. Use returned IDs and confirmed pane ownership, never directory-name guesses or a pane inferred from tab membership. Establish the other-repository nonmatch in an owned workspace created with `herdr workspace create --cwd "$HERDR_AUTORUN_TEST_ROOT/other-repo"` and attach it with `herdr worktree open --workspace <RETURNED_OTHER_WORKSPACE_ID> --path "$HERDR_AUTORUN_TEST_ROOT/other-repo" --focus`; inspect its actual doctor context before using it as the nonmatching target. Do not reuse a real repository or existing linked worktree, and do not bypass trust checks globally.

1. On this isolated server, obtain `herdr plugin config-dir han.tab-autorun` and verify `rules.toml` is absent. From a **different cwd** (for example, a disposable fixture below `$HERDR_AUTORUN_TEST_ROOT`, not the checkout), invoke `herdr plugin action invoke han.tab-autorun.init-config` in the owned disposable workspace, poll its log, and inspect the config path. The resulting file must equal the checkout's `rules.example.toml` bytes: active defaults but **all** rules commented, including `repo proof`. Before changing the starter, create a fresh owned tab with its returned workspace ID, record returned tab/root-pane/terminal IDs, read its initial pane successfully to establish no autorun proof, and invoke doctor in that context to confirm `skip`/`no_rule_match`; compare the unchanged starter bytes again. Ensure the initializer did not write to the caller cwd. Preserve a copy of this starter outside the config directory for later comparison.
2. Before another initializer invocation, replace the isolated `rules.toml` with a deliberately ordered, valid, **inert** rules file of distinctive bytes and set a distinctive file mode. Record bytes and mode, invoke init-config again from the other cwd, and confirm its completed log says the file already exists and leaves bytes, rule order, and mode unchanged. Restore the backed-up starter only inside isolated plugin config. Do not test overwrite against a real user's config.
3. In that starter, use the exact `repo_name` observed in **both** regular and linked doctor contexts, not `proof-repo` by assumption; review the command and replace `YOUR_REPO_NAME` in the first `repo proof` rule, then explicitly uncomment that entire `[[rules]]` / `[rules.when]` / `[rules.run]` block. Keep its command `echo HERDR_TAB_AUTORUN_PROOF` and no linked-worktree predicate. If starting instead from an older rules file with an earlier linked-worktree `skip`, explicitly remove or reorder that skip before expecting linked matches: first matching rule wins. Use the already attached ordinary checkout and linked worktree of **that same** fixture repository, plus the independently inspected other-repository fixture. Create owned tabs with `herdr tab create --workspace <RETURNED_WORKSPACE_ID> --no-focus --cwd <FIXTURE_CWD>` (the regular and linked cwd under their attached workspace, the other cwd under its own workspace); record each response's tab, root-pane, and terminal IDs and verify ownership against the pre-creation inventory. Both selected-repo tabs must show exactly one proof in their **initial** panes with successful reads and completed hook logs; the other repository must show no proof and doctor `no_rule_match`. Compare actual doctor contexts if another rule or repository identity unexpectedly matches; never count an unverified different repository as nonmatch. Read other panes successfully to establish no unrelated pane effect; a failed pane read is inconclusive, not absence. Splits and restored tabs are not substitutes for newly created tabs. Separately, if a workspace has no reported `repo_name`, the README's reviewed exact `cwd_glob` scoped to a doctor-confirmed cwd can be used instead; verify each intended cwd and a distinct nonmatching cwd with doctor before claiming coverage, rather than assuming repo metadata or broadening to an unconditional rule.
4. For manual scope, make an owned split with `herdr pane split --pane <OWNED_ROOT_PANE_ID> --direction right --cwd <FIXTURE_CWD> --no-focus`. Select an owned target using the harness's `tab focus` / checked `pane current` / `pane zoom` procedure, then invoke `herdr plugin action invoke han.tab-autorun.run-here` **without pane or tab flags**. Check the returned context workspace/tab/focused-pane IDs and completed log; uniquely identify the manual command output in the selected pane and confirm no new output in the other pane through successful `pane read` calls. If the default proof echo cannot distinguish preexisting output, use an additional reviewed, repository-scoped disposable marker-file command and verify both its marker and selected-pane output. Do not treat CLI exit 0, doctor matching, a marker alone, or a failed read as proof of the right-pane effect.
5. In an owned tab invoke `herdr plugin action invoke han.tab-autorun.doctor` and poll each returned log. Compare its `decision` fields with the config/context for: missing or unmatched rule → `skip`/`no_rule_match`; `[defaults] enabled = false` (including before manual run-here) → `skip`/`disabled`; an earlier explicitly matching `mode = "skip"` rule → `skip`/`rule_skip`; enabled proof rule with matching repo → `run`/`matched` and the selected rule; malformed TOML **or a later invalid rule after a valid matching rule** → `blocked`/`config_invalid`, diagnostic exit 1, and no effect. Benign doctor decisions exit 0. Save and restore isolated config bytes around each alteration. Doctor reports matching only: even `run`/`matched` neither executes the command nor guarantees shell readiness, rate capacity, pane claim, or completion. Verify effects independently via the actual new-tab or manual action logs and pane reads; an invalid config fails closed rather than allowing an earlier rule to execute.

Keep the restart/restore exercise below separate in a disposable named session; do not restart the ordinary harness server for this acceptance. Preserve the harness's refusal to clean up ambiguous or foreign terminals, restore original focus and preexisting rules, and retain fixtures if a surviving terminal might still use them. These steps are future acceptance checks, **not** claims that changed onboarding has passed a new live Herdr run; the recorded versioned results above remain historical.

## Proposed privacy-preserving pilot (not recruiting or running now)

After the changed product passes the isolated live gate above, propose five qualified, consenting macOS Herdr users who actually create new tabs in repositories; recruiting, invitations, and collection require accessible participants and consent. Interviews about the **current** native/manual workflow may occur during development without exposing people to the changed product; they do not count as pilot adoption. For every enrolment and attempt, report raw counts including installs that fail (Node/npm/native build or setup), initial configuration attempts, time to the first real task completed without staff intervention, and whether each user got a first successful real task. For seven days per user, record the number of **eligible** new-tab opportunities (at least two are needed for follow-up eligibility) and whether intentional reuse in a real task delivered business value. Ask for observations with consent; keep no command content, repository contents, prompts, or automatic telemetry. No eligible opportunities is **not** rejection; report it explicitly, not as a reuse failure.

Consider a next *limited* pilot only if at least 4/5 enrolled users reach first unaided real-task success, then at least four users have two or more eligible new-tab opportunities within seven days, and intentional valuable reuse occurs for at least 3/4 eligible users (or 4/5 if all five are eligible). Lower first-task activation calls for install/config rework; lower eligible reuse calls for reexamining user value. Too few participants or eligible opportunities is inconclusive, not a pass or failure. Any wrong-pane effect or unapproved command is an immediate stop, regardless of counts. Report all attempted and failed observations without extrapolating to a broader population; no pilot outcomes are claimed here.

## Manual restore/restart check

A restart/session-restore check is intentionally not automated: restarting a server can affect unrelated tabs and session state. Use a disposable scratch named session, not your normal session:

1. Start or select the scratch session with the `herdr --session autorun-probe` command prefix, link the checkout, and install a rule whose command writes a distinctive marker file in a scratch fixture.
2. Create one scratch tab with that prefix and record its tab ID, root pane ID, marker file, and the plugin-log count. Confirm the command ran once.
3. Restart the scratch server using the normal server restart procedure with the same `herdr --session autorun-probe` session. Allow session restore to finish.
4. Check the restored tab and plugin log. The old tab must not receive a new `tab.created` autorun and the marker/log count must not increase because restore emits no lifecycle hook.
5. Create a fresh scratch tab with the same prefix. It must autorun once, proving that native restore suppression did not disable genuine new-tab events.
6. Unlink the plugin and stop/remove the `autorun-probe` scratch session when finished.
